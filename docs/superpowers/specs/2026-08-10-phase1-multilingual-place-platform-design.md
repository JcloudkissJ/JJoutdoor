# Phase 1 설계 — 다국어 아웃도어 장소 플랫폼

- 작성일: 2026-08-10
- 상태: 설계 확정 대기
- 범위: Phase 1 (다국어 장소 정보 기반). 댓글·앱·수익화는 별도 Phase.

---

## 1. 배경

국내 산에서 외국인 등산객이 눈에 띄게 늘었다는 현장 관찰에서 출발한다. 이 사용자는
하나의 집단이 아니라 두 집단이며, 둘은 필요한 것이 다르다.

| 집단 | 언어 | 특징 | 필요 |
|---|---|---|---|
| 인바운드 관광객 | 영어, 중국어, 일본어 | 단기 체류, 재방문 없음 | 서울에서 반나절 안에 다녀올 곳 하나 |
| 국내 체류 외국인 | 몽골어, 싱할라어, 말레이어, 러시아어 | 노동자·유학생·이주민, 주말 반복 이용 | 거주지 근처, 반복 가능한 곳 |

두 집단이 공통으로 막히는 지점은 동일하다. **어떻게 가는지, 무엇을 챙기는지,
어디가 안전한지**를 모국어로 알 수 없다는 것.

기존 국내 등산 정보는 한국어 전용이고 대부분 서술형 글이다. 서술형은 번역
유지보수가 불가능하고 필터링도 되지 않는다. 이 구조적 차이가 본 프로젝트의
출발점이다.

## 2. 목적

1. **정확성** — 산림청, 국립공원공단, 지자체 등산로 정보를 교차 검증한다.
   거리·소요시간·난이도 등 핵심 수치는 공식 데이터에 근거한다.
2. **안전성** — 코스별 주의사항, 계절별 안전 가이드, 응급 상황 대처법을
   체계적으로 제공한다.
3. **접근성** — 8개 언어로 동등하게 제공한다.

## 3. Phase 1 범위

**포함**

- 장소(산) 데이터 모델 및 콘텐츠 15건
- 공공데이터 수집 및 교차 검증 파이프라인
- 안전 콘텐츠 (위험요소 카드, 계절 가이드, 응급 대처)
- 8개 언어 정적 사이트 (i18n, hreflang, sitemap)
- 두 개의 진입점 (반나절권 큐레이션 / 내 주변)
- 구조화 필드 기반 필터

**제외** — 이 Phase에서 만들지 않는다.

- 댓글, 로그인, 사용자 업로드
- 광고 및 수익화
- 모바일 앱
- 섬·낚시 **기능** (스키마 추상화만 수행)
- CMS 및 관리자 화면

## 4. 아키텍처

```
Astro (SSG)  →  Cloudflare Pages
콘텐츠  src/content/places/*.json      Git이 곧 DB
번역    src/i18n/{lang}.json           UI 라벨 사전
원본    data/raw/{source}/*.json       공공데이터 원본 보존
```

Phase 1에는 상시 서버가 존재하지 않는다. 서비스의 90%가 읽기 전용이므로 정적
생성으로 충분하며, 1인 개발에서 가장 큰 실패 요인인 운영 부담을 0으로 만든다.
8개 언어 × 산 100개로 늘어나도 빌드 시간이 증가할 뿐 런타임 비용은 발생하지 않는다.

Phase 2에서 댓글·인증이 필요해지면 Supabase(Postgres + Google OAuth)를 붙인다.
정적 콘텐츠와 동적 기능이 분리되어 있으므로 Phase 1 산출물은 재작업 없이 유지된다.

**선택하지 않은 대안**

- Next.js + 자체 백엔드: Phase 1에 과하며, 1인 운영에서 서버·DB 관리는 순 부채다.
- Python(FastAPI/Django): 개발자에게 익숙하지만 8개 언어 SEO를 정적 생성 없이
  구현하려면 손이 훨씬 많이 든다. 익숙함의 이득보다 손해가 크다.

## 5. 데이터 모델

### 5.1 Place

모든 장소는 단일 엔티티 `Place`로 표현하고 종류는 필드로 구분한다. 섬·낚시로
확장할 때 스키마 마이그레이션과 URL 변경을 피하기 위한 유일한 사전 작업이다.
기능은 산만 구현한다.

```jsonc
{
  "id": "inwangsan",
  "type": "mountain",              // mountain | island | fishing
  "slug": "inwangsan",
  "name_i18n": { "ko": "인왕산", "en": "Inwangsan", "...": "" },
  "region": { "sido": "11", "sigungu": "11110" },
  "coords": { "lat": 37.5800, "lng": 126.9585 },

  "metrics": {
    "elevation_m": 338,
    "distance_km": 3.2,
    "duration_min": 90,
    "difficulty": 1                // 1|2|3 — 라벨은 i18n 사전에서 조회
  },

  "access": {
    "transit": { "subway": true, "station_i18n": {}, "walk_min": 10, "bus_only": false },
    "signage_langs": ["ko", "en"],
    "restroom": true,
    "water_refill": true,
    "entry_fee_krw": 0,
    "open_hours": { "type": "seasonal", "detail": "" },
    "cell_coverage": "good"        // good | partial | none
  },

  "safety": {
    "hazards": ["slippery_rock", "steep_stair"],   // enum → 안전 카드에 매핑
    "sunset_caution": true
  },

  "text": {                        // 유일한 자유 서술. 언어당 3문장.
    "ko": { "summary": "", "caution1": "", "caution2": "" },
    "en": { "summary": "", "caution1": "", "caution2": "" }
  },

  "provenance": {}                 // 5.3 참조
}
```

**핵심 원칙: 구조화 필드는 언어 독립적이다.** `"약 1시간 30분"`이 아니라
`duration_min: 90`으로 저장하고, `"보통 / Moderate / Дунд"`는 라벨 사전에서
꺼낸다. 9번째 언어를 추가해도 장소 데이터는 손대지 않는다.

이 원칙의 부수 효과로 검색·필터가 공짜로 따라온다. 서술문은 필터링할 수 없지만
구조화 필드는 가능하다.

### 5.2 signage_langs — 자체 수집 데이터

`signage_langs`(등산로 표지판에 표기된 언어)는 공공데이터에 존재하지 않으며
직접 현장에서 채워야 한다. 그러나 이 정보는 외국인의 장소 선택을 실제로 가르는
요소이고, 어느 국내 서비스도 제공하지 않는다. 수집 비용이 곧 진입장벽이 된다.

Phase 1에서는 확인된 장소만 값을 채우고, 미확인은 `null`로 두어 "정보 없음"으로
표시한다. 추측해서 채우지 않는다.

### 5.3 provenance — 출처와 검증 상태

"공식 데이터 기반 교차검증"을 표방하는 이상, 그 근거를 데이터에 남기고 화면에
표시해야 한다. 표시할 수 없는 검증은 마케팅 문구일 뿐이다.

```jsonc
"provenance": {
  "sources": [
    { "org": "knps", "dataset": "탐방로 정보", "url": "", "fetched_at": "2026-08-10" },
    { "org": "forest_service", "dataset": "등산로 정보", "url": "", "fetched_at": "2026-08-10" }
  ],
  "verification": {
    "status": "verified",          // verified | single_source | conflict
    "checked_fields": ["distance_km", "duration_min"],
    "note": ""
  }
}
```

각 장소 상세 페이지 하단에 출처 기관과 조회 일자를 표기한다. 공공데이터포털
데이터는 다수가 출처 표시 조건을 수반하므로 준수 의무이기도 하다.

### 5.4 안전 콘텐츠 — 장소 수에 비례하지 않는 고정 자산

안전 정보는 서술형이 불가피하지만, **장소 수와 무관하게 개수가 고정**되므로
번역 부담이 폭발하지 않는다. 이것이 안전을 핵심 기둥으로 세울 수 있는 이유다.

| 종류 | 개수 | 산 수와의 관계 |
|---|---|---|
| 위험요소 카드 (`hazards` enum별 설명) | 약 12 | 무관. 한 번 번역해 모든 장소에서 재사용 |
| 계절별 안전 가이드 | 4 | 무관 |
| 응급 상황 대처 | 6–8 | 무관 |

```jsonc
// src/content/safety/*.json
{
  "id": "emergency-call-119",
  "category": "emergency",         // hazard | seasonal | emergency
  "season": null,
  "text": {
    "ko": { "title": "", "body": [] },
    "en": { "title": "", "body": [] }
  }
}
```

응급 대처 콘텐츠에는 외국인 특화 항목을 반드시 포함한다. 119 신고 시 다국어
통역 연결 방법과 산악 위치표지판 번호 체계는 구조 요청의 핵심인데, 외국인
이용자는 존재 자체를 모른다.

## 6. 데이터 파이프라인

```
scripts/fetch/{knps,forest_service,local}.*   →  data/raw/{source}/*.json
scripts/reconcile.*                           →  src/content/places/*.json
```

원본은 항상 보존한다. 재현 불가능한 가공은 검증을 주장할 수 없다.

**대조 규칙** (거리·소요시간·고도)

| 조건 | 판정 |
|---|---|
| 2개 이상 출처가 오차 범위 내 일치 | `verified` |
| 단일 출처만 존재 | `single_source` |
| 출처 간 오차 범위 초과 | `conflict` → 수동 확인 큐 |

오차 허용치는 초기값 ±10%로 두되 조정 가능한 상수로 관리한다. 거리와 소요시간은
기관마다 측정 기준과 기준 체력이 달라 실제 편차가 크다. 이 값은 실데이터를 보고
조정해야 하는 튜닝 지점이다.

`conflict` 상태는 숨기지 않고 "출처 간 정보가 다름"으로 표시한다. 불확실성을
드러내는 편이 틀린 확신보다 안전하다.

구체적인 API 엔드포인트와 파라미터는 구현 시 공공데이터포털에서 확인한다. 본
설계에서는 기관과 데이터 성격까지만 확정한다.

## 7. 번역 정책 — 2등급 분리

| 등급 | 대상 | 방식 |
|---|---|---|
| A (사람 검수 필수) | 안전 가이드, 응급 대처, 위험요소 카드, 경고 문구 | 기계번역 초안 허용, **게시 전 사람 검수 의무** |
| B (자동 허용) | 장소 요약·소개, UI 라벨 | 기계번역 후 게시 가능 |

안전 정보의 오역은 사람을 다치게 한다. A등급 콘텐츠는 개수가 고정(약 25건)이므로
8개 언어 검수가 현실적으로 가능하다.

언어: `en ko mn zh ja ms si ru` — 영어를 공통 허브로 삼는다.

> 참고: "스리랑카어"라는 언어는 존재하지 않는다. 싱할라어(`si`)와 타밀어(`ta`)
> 두 개이며 본 설계는 싱할라어를 채택한다. 타밀어는 인도 남부·말레이시아에서도
> 통용되어 커버리지가 넓으므로 추후 확장 1순위다.

중국어 사용자 중 중국 본토 접속자는 Google 서비스에 접근할 수 없다. Phase 2에서
로그인을 도입하더라도 **읽기는 항상 비로그인으로 완전히 가능해야 한다.**

## 8. URL 및 i18n

```
/{lang}/                        홈
/{lang}/mountain/               목록 + 필터
/{lang}/mountain/{slug}         상세
/{lang}/near/{region}           내 주변           — 체류자 진입점
/{lang}/half-day-from-seoul     반나절권 큐레이션  — 관광객 진입점
/{lang}/safety/                 안전 가이드 허브
/{lang}/safety/{slug}           개별 안전 문서
```

`/{lang}/{type}/{slug}` 구조를 처음부터 고정한다. `/{lang}/{slug}`로 시작하면
섬·낚시 추가 시 전체 URL 마이그레이션과 축적된 검색 순위 손실이 발생한다.

전 언어 상호 `hreflang` 링크와 `sitemap.xml`을 빌드 시 자동 생성한다.

## 9. 두 진입점, 하나의 데이터

두 타깃을 별도 사이트로 나누지 않는다. 동일한 `Place` 컬렉션에 대해 정렬과
필터만 다르게 적용한다. 콘텐츠 중복이 없고 구현 부담도 거의 없다.

- **관광객**: 홈 → `half-day-from-seoul` — 서울 기준 이동시간과 총 소요시간으로 선별
- **체류자**: 홈 → 지역 선택 또는 위치 기반 → `near/{region}`

## 10. 필터

지역 · 소요시간 · 난이도 · 대중교통 접근 · **표지판 언어** · 화장실 · 입장료

모두 구조화 필드에서 직접 파생되며 8개 언어 전부에서 동일하게 동작한다.

## 11. 초기 콘텐츠 — 산 15개

- 서울·경기 8개 — 관광객 및 수도권 체류자 커버
- 그 외 7개 — **체류 외국인 밀집 지역 인근**(안산, 화성, 김해 등)에서 선정

두 타깃을 UI가 아니라 데이터 선정 단계에서 나눠 담는다.

공공데이터 품질이 가장 정비된 국립공원 관할 코스를 우선 포함해 파이프라인을
먼저 검증하고, 이후 지자체 데이터로 확장한다.

빌드 산출물 규모는 언어당 약 50페이지다.

```
홈 1 + 목록 1 + 장소 상세 15 + 지역별 10 + 큐레이션 1
+ 안전 허브 1 + 안전 문서 23  ≈  52
```

8개 언어 전체로 **약 420페이지**. SSG 빌드로 수 초 내 처리되는 규모이며, 장소를
100개로 늘려도 언어당 약 140페이지, 전체 1,100페이지 수준이라 여전히 정적 생성이
유효하다.

## 12. 완료 기준

Phase 1의 출시 언어는 **영어와 한국어 2개**다. 나머지 6개 언어는 순차 확장하며,
Phase 1의 책임은 "언어를 하나 추가하는 작업이 반복 가능한 정형 작업이 되도록
구조를 갖추는 것"까지다. 8개 언어 동시 출시를 완료 조건으로 두면 Phase 1이
끝나지 않는다.

**출시 조건**

- [ ] `en`, `ko` 각 페이지가 검색엔진에 개별 인덱싱, hreflang 검증 통과
- [ ] 필터가 두 언어에서 동일하게 동작
- [ ] 375px 뷰포트 가로 오버플로 0
- [ ] Lighthouse SEO 100, 접근성 95 이상
- [ ] 산 15건 전부 `provenance.sources` 2건 이상 또는 `single_source` 명시
- [ ] A등급(안전) 콘텐츠 `en`, `ko` 사람 검수 완료
- [ ] `conflict` 판정 데이터가 화면에 정직하게 표시됨

**확장 준비 조건** — 3번째 언어를 붙일 때 코드 수정이 필요 없어야 한다.

- [ ] 언어 추가가 `i18n/{lang}.json` 생성 + 장소별 `text.{lang}` 채우기로만 완결
- [ ] 라우팅·hreflang·sitemap이 언어 목록에서 자동 파생 (하드코딩 없음)
- [ ] 스크립트별 폰트가 해당 언어 페이지에서만 로딩됨
- [ ] 미번역 필드의 폴백 동작 정의 및 검증 (영어로 폴백, 누락 표시)

## 13. 리스크

## 14. Phase 2 이후 (미확정, 참고용)

- **Phase 2** 인증 + 장소별 댓글. Google OAuth 우선, 앱 대비 다중 provider 스키마.
  댓글 원문 + 번역 토글은 선택이 아니라 필수 구조 — 언어별로 파편화되면 각
  언어권 댓글 수가 0에 수렴한다. 다국어 모더레이션 필요.
- **Phase 3** 수익화. 디스플레이 광고는 이 트래픽 규모에서 주 수익원이 되기
  어렵다. 교통·셔틀 중개, 장비 렌탈 제휴, 산 아래 상권 리스팅, 관광 정책
  지원사업이 더 현실적인 경로다.
- **Phase 4** 도메인 확장 (섬 → 낚시). 낚시는 규제·면허·금지구역 등 안전 축이
  산과 다르므로 별도 설계가 필요하다.
- **Phase 5** 모바일 앱. 오프라인 지도와 GPS 트랙이 필요해지는 시점이 앱의
  진짜 이유다. 소셜 로그인 제공 시 Apple 로그인 병행이 심사 요건이다.

각 Phase는 독립된 스펙 → 계획 → 구현 주기를 갖는다.
