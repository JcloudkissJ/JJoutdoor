# 미결 쟁점 — provenance의 단위와 교차검증 전제

- 작성일: 2026-08-13

- 영향 범위: `src/content/config.ts` 스키마, `src/components/ProvenanceBlock.astro`, `src/lib/reconcile.ts` 호출부, 기존 콘텐츠 3건
- 배경: 2026-08-13 공공데이터 조사 결과

## 1. 무엇이 어긋났는가

Phase 1 설계(§2 목적 1)는 이렇게 적었다.

> **정확성** — 산림청, 국립공원공단, 지자체 등산로 정보를 교차 검증한다.

이 문장은 **여러 기관이 같은 수치를 제공한다**는 전제 위에 서 있다. `reconcile()`은 그 전제대로
만들어졌다 — 여러 판독값을 받아 중앙값을 내고 편차로 `verified` / `single_source` / `conflict`를
판정한다.

2026-08-13 조사에서 확인한 실제 데이터 지형은 다르다.

| 층위 | 필드 | 출처 | 형식 |
|---|---|---|---|
| 산 단위 | 이름, 높이, 소재지, 좌표 | 산림청 산정보 API | REST/XML, 인증키 필요 |
| 노선 단위 | 거리, 소요시간, 난이도, 편의시설 | 산림청 등산로 / 국립공원공단 탐방로 | SHP·GeoJSON·CSV 파일 |

**필드마다 출처가 하나씩일 가능성이 높다.** 그렇다면 `reconcile()`은 항상 `single_source`를
반환하고, `verified`와 `conflict` 분기는 실행되지 않는다. 교차검증이라는 표현을 쓸 근거가 없어진다.

아직 확정은 아니다. 국립공원 관할 산은 산림청과 국립공원공단 데이터가 겹칠 수 있고,
고도는 두 출처 모두에 있을 가능성이 있다. **겹침의 실제 범위는 데이터를 받아봐야 안다.**

## 2. 스키마와 로직의 단위 불일치

전제와 별개로, 구조 자체에 이미 어긋남이 있다.

`reconcile()`은 **필드 단위**로 동작한다 — 호출 한 번이 판독값 배열 하나를 받아 상태 하나를 낸다.

```ts
reconcile([{ org: 'forest_service', value: 3.2 }]) // → { value, verification: { status, spread } }
```

그런데 스키마는 **장소 단위**로 상태 하나만 저장한다.

```jsonc
"provenance": {
  "sources": [ /* ... */ ],
  "verification": {
    "status": "single_source",          // ← 장소 전체에 상태 하나
    "checked_fields": ["distance_km"]   // ← 어느 필드를 봤는지만, 각각의 결과는 없음
  }
}
```

고도는 두 출처가 일치하고 거리는 한 출처뿐인 장소를 표현할 방법이 없다. `checked_fields`는
"무엇을 확인했는가"만 담고 "각각 어떤 결과였는가"는 담지 못한다.

`ProvenanceBlock`은 이 단일 상태로 문구 하나를 렌더링한다. 즉 **어느 수치가 검증됐고 어느
수치가 아닌지 독자가 알 수 없다.** 이는 프로젝트가 반복해서 지켜온 규칙(미확인을 확인된 것처럼
보이지 않게 한다)의 정신에 어긋난다.

## 3. 선택지

### A. 장소 단위 유지 + 집계 규칙 정의

가장 나쁜 상태를 장소 상태로 삼는다(`conflict` > `single_source` > `verified`).

- **비용**: 없음. 스키마·UI 무변경
- **문제**: 다섯 필드가 검증됐고 하나만 단일 출처인 장소가 "단일 공식 출처"로 표시된다. 반대로
  한 필드의 불일치가 장소 전체를 `conflict`로 만들면서 **어느 수치가 문제인지 말하지 않는다**

### B. 필드 단위로 이동

```jsonc
"provenance": {
  "sources": [ /* ... */ ],
  "fields": {
    "elevation_m": { "status": "verified",      "orgs": ["forest_service", "knps"], "spread": 0.003 },
    "distance_km": { "status": "single_source", "orgs": ["forest_service"] }
  }
}
```

- **이득**: 정직하고 정밀하다. `MetricRow`가 분쟁 중인 수치 옆에만 표시할 수 있다
- **비용**: 스키마 변경(Task 6), `ProvenanceBlock` 개편(Task 9), `MetricRow`에 상태 전달,
  기존 콘텐츠 3건 재작성, 스키마 테스트 추가

### C. 필드 단위 저장 + 장소 요약 파생

B로 저장하고 헤더용 요약만 계산해서 둘 다 보여준다.

- **이득**: 개요와 세부를 모두 제공
- **비용**: 가장 큼

## 4. 결정 기준 — 데이터를 보고 무엇을 확인할 것인가

선택은 취향이 아니라 다음 측정으로 정한다.

1. **필드별 출처 수 분포.** 초기 3개 장소에 대해 `elevation_m` / `distance_km` /
   `duration_min` / `difficulty` 각각 몇 개 기관이 값을 제공하는가?
2. **겹침이 존재하는가.** 두 출처 이상을 가진 필드가 하나라도 있는가?
3. **겹치는 값이 실제로 일치하는가.** `TOLERANCE = 0.1` 기준에서 `verified`가 나오는가,
   아니면 기관 간 측정 기준 차이로 대부분 `conflict`가 되는가?

측정 결과에 따른 판단:

| 관측 | 결론 |
|---|---|
| 모든 필드가 단일 출처 | **A로도 충분.** 필드 단위로 나눠도 전부 같은 값이라 정보 이득이 없다. 대신 §5의 문구 문제를 반드시 처리한다 |
| 일부 필드만 다중 출처 | **B가 정당화된다.** 검증된 수치와 아닌 수치가 한 장소 안에 공존하므로 구분해야 한다 |
| 다중 출처가 흔하고 불일치도 잦음 | **B + `TOLERANCE` 재조정.** 기관 간 측정 기준 차이가 크다는 뜻이며, 10%가 적정한지 실측으로 다시 정한다 |

## 5. 문구 문제 — 이것은 스키마와 별개로 반드시 처리한다

`src/i18n/en.json`에 이 문자열이 있다.

```json
"provenance.verified": "Cross-checked against two or more official sources"
```

교차 확인이 한 번도 일어나지 않는다면 이 문자열은 죽은 코드이고, 설계 문서 §2의
"교차 검증한다"는 목적 진술도 사실과 어긋난다.

그 경우 할 일은 둘 중 하나다.

- **표현을 실제에 맞춘다** — "공식 출처 기반"으로 낮추고, 교차검증은 가능한 필드에 한해
  적용한다고 명시
- **두 번째 출처를 실제로 확보한다** — 지자체 데이터, 국립공원공단, 또는 현장 확인을
  독립 출처로 취급

후자와 관련해 정해야 할 것이 하나 더 있다. **무엇을 "두 번째 출처"로 인정하는가?**
`signage_langs`는 이미 현장 수집을 전제로 하고 있다(공공데이터에 없는 필드). 현장 확인을
기관 데이터와 대등한 출처로 셈할 것인지, 아니면 별도 등급으로 둘 것인지는 미정이다.

## 6. 지금 결정하지 않는 이유

`reconcile()`은 이미 만들어졌고 12개 테스트로 검증됐으며 **호출자가 없다.** 호출부를 만들기
전에 이 쟁점을 정리하는 것이 순서다. 코드를 먼저 붙이면 전부 `single_source`인 파이프라인을
완성한 뒤에야 전제가 틀렸음을 알게 된다.

이 문서의 역할은 결정을 미루는 것이 아니라 **결정에 필요한 측정을 먼저 정의하는 것**이다.
